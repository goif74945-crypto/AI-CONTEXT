# AI.AI architecture, authority and implementation boundary

## Authority

A user's current, local, intentional instruction is authoritative for actions in the authorized local workspace and consented OS sessions. A proposed LLM plan, browser page, transcribed voice input, documentation and connected-device UI content are **untrusted data** until a user reviews the plan. A connected phone must authorize ADB debugging itself.

## Architecture

1. **Client:** browser HTML/CSS/JS on localhost. Text is entered manually; Web Speech API provides opt-in mic transcription; WebAudio analyzes high-pass audio transients for a time-limited double clap.
2. **Planner:** deterministic exact command parser for simple single/multi-step workflows; optional OpenAI model returns JSON. Neither executes commands. Proposed JSON goes through Pydantic strict shape validation, bounded numeric and string limits, and a known tool namespace.
3. **Approval:** single-use plan ID generated by cryptographic randomness, stored server-side with TTL 180 seconds; only that server-side plan can execute. A typed literal approval field is mandatory. Manual button press or explicit microphone arming is the visible authorization step. High-risk action types are excluded from clap activation.
4. **Transport and authorization:** FastAPI bound to `127.0.0.1`, Host/Origin verification, same-origin ephemeral session token. No internet-facing listener, authentication pairing, websocket remote bridge or external session allowed.
5. **Single-writer executor:** executes serially with per-step completion results. The Stop button sets an event read between actions and while waiting on child Python processes; existing direct GUI/ADB calls cannot be instantaneously cancelled.
6. **Capabilities:** Desktop PyAutoGUI, restricted app launcher, local-file paths bounded to `workspace`, trusted Python scripts (opt-in), Android Debug Bridge on an authorized connected device.

## Explicitly not equivalent to full automation

This version does not inspect screenshots to decide where to click, understand arbitrary program UIs, manipulate every app, launch long-lived unattended jobs, or run on Android as an installed native app. Desktop OS permission dialogs, Android accessibility requirements and iOS sandbox boundaries remain authoritative. A generic application click can have high impact and should be reviewed carefully.

## Branch strategy

Repository `AI.AI` targets **only `main`**. Every code write in this deliverable was local. Do not write to the existing NEXY.AI product repository. Do not infer or transplant NEXY-IGNIS spec requirements into this independent project.

## Acceptance evidence and limitations

- Strict action schema and parser behavior: automated unit tests.
- Plan creation and one-time approval: FastAPI HTTP tests + real localhost HTTP smoke.
- Local file IO and trusted Python subprocess: real filesystem and subprocess tests.
- Android ADB argument construction: mocked unit tests. Physical device remains NOT_VERIFIED.
- Browser voice and double clap: client source inspected and JS syntax checked, not physical microphone tested.
- Desktop GUI: OS adapter code exists, but real mouse/keyboard actions are NOT_VERIFIED on the user's machine.
- GitHub CI: workflow authored, NOT_EXECUTED on GitHub.
